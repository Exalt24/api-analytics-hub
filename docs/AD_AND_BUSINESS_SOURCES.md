# Ad and business system sources

What the Google Ads, TikTok, Square, QuickBooks Online and Shopmonkey connectors (`app/connectors/google_ads.py`, `tiktok.py`, `square.py`, `quickbooks.py`, `shopmonkey.py`) and their stand-in servers (`*_fake.py`) were written from. Every page below was loaded in a real browser on 2026-11-06 or 2026-11-07 and saved as text; a quote under a fact is copied from the saved page. A fact the pages did not give is marked UNVERIFIED here and in the code, and it stays that way until a real account answers.

No Google Ads account, TikTok advertiser, Square seller, QuickBooks company or Shopmonkey shop is held and none was used. Each connector has only run against its stand-in, so nothing here is a statement that a vendor accepts these requests. A stand-in is written from these pages and refuses what they say the vendor refuses (`tests/test_*_connector.py`, the last section of each).

The shared rules (integer minor units, half up rounding, a float refused, one bounded retry loop) are in `app/connectors/common.py` and are checked over many seeded worlds in `tests/test_vendor_common.py`.

## Google Ads

**The call.** Pages: https://developers.google.com/google-ads/api/rest/common/search and https://developers.google.com/google-ads/api/rest/overview (updated 2026-10-30).
"Both Search and SearchStream use the same base URL: https://googleads.googleapis.com/v26/customers/CUSTOMER_ID/googleAds". The connector sends `POST .../v26/customers/{id}/googleAds:search` with `{"query": ..., "pageToken": ...}`.
"The Search method returns data in fixed size pages of 10,000 rows, enabling you to iterate over a result set using pagination." and "If there are more than 10,000 rows in the results a nextPageToken is returned in the response". Search is used so a cursor can name a page; SearchStream "streams the entire result set back in a single response" and its results "are wrapped in a JSON array".
The version is the one every REST example on https://developers.google.com/google-ads/api/rest/examples uses (`API_VERSION="26"`). UNVERIFIED: which version is current beyond the examples; the version is a constant in the connector.

**No developer token.** Page: https://developers.google.com/google-ads/api/docs/api-policy/developer-token. "Can I stop sending developer tokens as part of my API requests? Yes, you can stop sending developer tokens as part of your API requests." The authorization page (https://developers.google.com/google-ads/api/rest/auth) lists `Authorization: Bearer` and `login-customer-id` and no developer token header, and none of the REST examples carries one. The connector sends none. UNVERIFIED: whether an account still on the old programme is refused without one.
"`login-customer-id` ... represents the Google Ads customer ID of the manager making the API call ... be sure to remove any hyphens". The connector strips hyphens from both ids and sends the header only when it is given.

**The query.** Pages: https://developers.google.com/google-ads/api/docs/query/grammar and https://developers.google.com/google-ads/api/docs/reporting/segmentation.
`SELECT segments.date, customer.currency_code, metrics.cost_micros, metrics.impressions, metrics.clicks, metrics.conversions, metrics.conversions_value FROM customer WHERE segments.date >= '..' AND segments.date <= '..'`. The grammar allows `>=` and `<=` joined by `AND`, and "Valid: This query returns campaign names and clicks segmented by date for all days in the inclusive date range" shows the inclusive form, so the half open window end is moved back one day.
"If any of these segments are in the SELECT clause, a finite date range composed of core date segments must be specified in the WHERE clause." The stand-in refuses a `segments.date` select without one (`CANNOT_SELECT_WITHOUT_DATE_RANGE`).
"Granular date segments (segments.date, segments.week, and segments.hour) support a lookback window of up to 37 months. Queries exceeding this range return DateRangeError.REQUESTED_DATE_GRANULARITY_NOT_SUPPORTED in v24 and later". The registry declares 37 months of history and the stand-in refuses the older range with that error.

**The response.** Page: https://developers.google.com/google-ads/api/rest/design/json-mappings. "Identifiers are transformed from snake_case (in protocol buffers) to lowerCamelCase in JSON. ... the results of a query in REST are returned as normal JSON objects and have their identifiers in lowerCamelCase." The connector reads `segments.date`, `customer.currencyCode`, `metrics.costMicros`, `metrics.impressions`, `metrics.clicks`, `metrics.conversions`, `metrics.conversionsValue`.
Types, from https://developers.google.com/google-ads/api/fields/v26/metrics: `metrics.cost_micros` is INT64 ("The sum of your cost-per-click (CPC) and cost-per-thousand impressions (CPM) costs during this period."), `metrics.clicks` and `metrics.impressions` are INT64. Protocol buffer JSON sends an int64 as a string, which is the protobuf rule the json-mappings page points at, so the connector accepts a numeric string for the three and refuses a float. `metrics.conversions` and `metrics.conversions_value` are doubles: "The number of conversions. This only includes conversion actions which include_in_conversions_metric attribute is set to true." They are JSON numbers, so the response is parsed with `parse_float=Decimal` and nothing passes through a binary float.
**Money.** `cost_micros` is millionths of the account's currency (UNVERIFIED on the pages read: the field description says "cost" and the name says micros; the connector reads it as one millionth of a major unit, the way the field is named). `customer.currency_code` is "The currency in which the account operates. A subset of the currency codes from the ISO 4217 standard is supported." The connector stores minor units, takes the currency from each row, refuses a row without one and a window whose rows name two.
**Conversions are stored in thousandths** (`ad_conversions`, unit `milli_count`) because a double can be fractional. UNVERIFIED: whether a zero double is sent or left out. The connector reads an absent `conversions` or `conversionsValue` as 0 because every metric was selected; the stand-in can do both (`omit_zero_doubles`) and a test pins the reading.
UNVERIFIED: whether `conversions_value` is in the account's currency. The connector stores it with the row's currency.

**A day with no row.** https://developers.google.com/google-ads/api/docs/reporting/zero-metrics ("Zero metrics") says zero metric rows appear for entities that are ineligible or were paused in the range, and how to exclude them. UNVERIFIED: whether `FROM customer` with `segments.date` returns a row for a day with no activity. The stand-in sends a row only for a day it was given, and the report tells a quiet day from a day nobody looked at from the sync runs.

**Local Services Ads leads.** Page: https://developers.google.com/google-ads/api/fields/v26/local_services_lead. `local_services_lead.creation_date_time`: "The date time at which lead was created by Local Services Ads. The format is "YYYY-MM-DD HH:MM:SS" in the Google Ads account's timezone." and `local_services_lead.lead_type`: "Type of Local Services lead: phone, message, booking, etc." With `local_services=True` the connector runs `SELECT local_services_lead.creation_date_time, local_services_lead.lead_type FROM local_services_lead WHERE local_services_lead.creation_date_time >= '.. 00:00:00' AND local_services_lead.creation_date_time < '.. 00:00:00'` and counts the leads per day. A day with no lead is a zero. UNVERIFIED: that the field is filterable with that string form (the page says "Filterable True" and gives the format, not a filter example); a lead outside the window is refused rather than counted.

**Errors.** Page: https://developers.google.com/google-ads/api/docs/best-practices/understand-api-errors. The body is a Status object `{"code", "message", "status", "details": [GoogleAdsFailure ...]}` and the table maps `UNAUTHENTICATED` to 401, `PERMISSION_DENIED` to 403, `RESOURCE_EXHAUSTED` to 429, `UNAVAILABLE` to 503, `INTERNAL` to 500, `DEADLINE_EXCEEDED` to 504, `UNKNOWN` to 500, `ABORTED` to 409, `INVALID_ARGUMENT` to 400, `NOT_FOUND` to 404. "Retry only for transient server errors such as UNAVAILABLE, DEADLINE_EXCEEDED, INTERNAL, UNKNOWN, and ABORTED."

| Status | The connector does |
|---|---|
| `UNAUTHENTICATED` | `AuthExpired`, retryable after a new token |
| `PERMISSION_DENIED` | `AuthRevoked`, a person must fix the access |
| `RESOURCE_EXHAUSTED`, `UNAVAILABLE`, `INTERNAL`, `DEADLINE_EXCEEDED`, `UNKNOWN`, `ABORTED` | retried with a bound, then `RateLimited` |
| anything else, including `INVALID_ARGUMENT` | `UpstreamBroken`, not retried |

The status string is read before the HTTP status, so an error object inside a 200 is an error. UNVERIFIED: a `google.rpc.RetryInfo` entry (`retryDelay: "30s"`) in `details`; the pages read do not show one, the connector uses it when present, and a numeric `Retry-After` header otherwise.
**Rate limits.** https://developers.google.com/google-ads/api/docs/best-practices/rate-limits: "Requests that violate rate limits are rejected with the error: RESOURCE_TEMPORARILY_EXHAUSTED." and "use an exponential backoff policy with randomized jitter". The connector backs off that way, bounded, and hands a wait longer than its cap to the runner.

## TikTok

**The call.** Pages: https://business-api.tiktok.com/portal/docs/basic-reports/v1.3 and the Run a synchronous report page (https://business-api.tiktok.com/gateway/docs/index?doc_id=1738864778664961).
"Use /report/integrated/get/ and specify the following settings." The example is `GET https://business-api.tiktok.com/open_api/v1.3/report/integrated/get/?advertiser_id=..&service_type=AUCTION&data_level=AUCTION_AD&report_type=BASIC&dimensions=["ad_id"]&metrics=["clicks"]&start_date=..&end_date=..` with `--header 'Access-Token:..'`. The connector sends `data_level=AUCTION_ADVERTISER` with the dimensions `["advertiser_id","stat_time_day"]`, which the Basic reports page shows for an advertiser level query.
"If you include stat_time_day in the value of the dimensions field to query daily breakdown data, you can retrieve data for a maximum of 30 days." A longer window is cut into runs of at most 30 days.
"The default page size is 10." The connector asks for 200, the figure the Basic reports use cases show; UNVERIFIED: the largest `page_size` TikTok accepts.
UNVERIFIED: whether `end_date` is inclusive. The page says "Time range: If you want to get data in a time range, you need to specify start_date and end_date." The connector treats it as inclusive and sends the run's last day; a row outside the run is refused, so a mismatch would surface and not be written.
UNVERIFIED: the exact form of `stat_time_day` in a row. The connector accepts `YYYY-MM-DD` and `YYYY-MM-DD HH:MM:SS` and the stand-in sends the second.

**The response.** Same example page: `{"code": 0, "message": "OK", "request_id": .., "data": {"page_info": {"total_number", "total_page", "page_size", "page"}, "list": [{"dimensions": {..}, "metrics": {"clicks": "34"}}]}}`. Every metric is a string. Metric names and meanings from https://business-api.tiktok.com/portal/docs/basic-reports-supported-metrics/v1.3: `spend` ("Sum of your total ad spend."), `impressions`, `clicks` ("Number of clicks from your ads to a specified destination."), `conversion` ("Number of times your ad resulted in the optimization event you selected."), and `currency` ("The currency code, e. g. USD. Note that if you want to use currency as metrics, then the dimensions field in your request must include adgroup_id/ad_id/campaign_id/advertiser_id."). The stand-in refuses `currency` without one of those dimensions.
**A day with no data.** Reporting FAQs (https://business-api.tiktok.com/portal/docs/reporting-faqs/v1.3), Q5: "When stat_time_day is specified in the dimensions, an empty list object is likely to be returned in the response, because metrics with no data are filtered out." A missing day is a quiet day.
**Truncation.** Same FAQs: for a report over more than 20,000 ads only the newest 20,000 are processed, and "In the Response Header, you will see X-Tt-Ads-Throttle". An advertiser level report is not ad level, but the figures would be incomplete if it happened, so the connector refuses a report that carries that header.
**Data latency.** https://business-api.tiktok.com/portal/docs/data-latency-for-reports/v1.3: real-time data "will be adjusted the following day to align with Offline Data", and the FAQs advise pulling T-1 "after 8:00 (UTC+0)". The default sync window ends twelve hours behind UTC like the others; UNVERIFIED how long a recent day stays provisional.
**The advertiser.** https://business-api.tiktok.com/portal/docs/get-ad-account-details/v1.3: `GET /open_api/v1.3/advertiser/info/` with `advertiser_ids` and `fields`; the response has `status` (example `STATUS_ENABLE`), `currency` ("Type of currency used by the ad account, in ISO 4217 code format.") and `timezone`. `verify()` reads these and refuses an advertiser that is not `STATUS_ENABLE`.

**Errors.** Return codes appendix (https://business-api.tiktok.com/gateway/docs/index?doc_id=1737172488964097). The envelope's `code` is read before the HTTP status.
| Code | The page says | The connector does |
|---|---|---|
| 40105 | "Invalid or incorrect access token." | `AuthExpired` |
| 40001, 40106 | "No permission to perform the related operation." / "The core user is invalid." | `AuthRevoked` |
| 40016, 40100 | "Requests made too frequently." (developer application level) | retried with a bound |
| 40133 | "Requests made too frequently." (advertiser level, "Advertiser ({ID})'s QPS ({current QPS}) reaches QPS limit") | retried with a bound |
| 50000, 50002, 51305, 60001 | "System error", "Error processing request on TikTok side", "Satellite service error", "The system is in maintenance" | retried with a bound |
| 40000, 40002 and any other | "The parameters provided are invalid.", "Parameter error." | `UpstreamBroken`, not retried |

UNVERIFIED: the HTTP status TikTok puts on these (the stand-in uses 200 with a non-zero code; the connector also maps 401, 403, 429 and 5xx when no code is present), and a `Retry-After` header. UNVERIFIED: the numeric rate limit of `/report/integrated/get/`; the appendix points at a Rate limits page that was not read, so pacing is by error only.

## Square

**The call.** Page: https://developer.squareup.com/reference/square/payments-api/list-payments (API version 2026-09-16).
`GET /v2/payments`. "The maximum results per page is 100." `begin_time`: "Indicates the start of the time range to retrieve payments for, in RFC 3339 format. The range is determined using the created_at field for each Payment. Inclusive." `end_time`: the same range, with no word on inclusivity (UNVERIFIED; the connector asks for the next local midnight and treats a payment at exactly that instant as the next day's, so either reading gives one answer). `sort_order` is `ASC` or `DESC` (default). `limit`: "The default value of 100 is also the maximum allowed value. If the provided value is greater than 100, it is ignored and the default value is used instead." `cursor`: "The pagination cursor to be used in a subsequent request. If empty, this is the final response." The page also says "Results are eventually consistent, and new payments or changes to payments might take several seconds to appear", so the default window ends twelve hours behind UTC.
Headers, from the curl example on https://developer.squareup.com/reference/square/locations-api/list-locations (the pagination page's examples show the same two): `Square-Version: 2026-09-16` and `Authorization: Bearer ACCESS_TOKEN`; base `https://connect.squareup.com` (and `https://connect.squareupsandbox.com` for the sandbox).

**The payment.** https://developer.squareup.com/reference/square/objects/Payment: `id`, `created_at` ("in RFC 3339 format"), `status` ("APPROVED, PENDING, COMPLETED, CANCELED, or FAILED"), `amount_money` ("The amount processed for this payment, not including tip_money."), `total_money` ("including amount_money and tip_money. This amount is specified in the smallest denomination of the applicable currency"), `refunded_money` ("The total amount of the payment refunded to date."), `location_id`. Money is `{"amount": integer, "currency": ..}`. Only COMPLETED is counted. **A refund is counted on the day of the payment it refunds**, because the payment carries the total refunded to date and no refund date; the Refunds API would give that date and is not read (a stated limit).
**The location.** https://developer.squareup.com/reference/square/objects/Location: `timezone` ("The IANA time zone identifier for the time zone of the location. For example, America/Los_Angeles."), `currency` ("The currency used for all transactions at this location, in ISO 4217 format."), `status`. `GET /v2/locations` ("Provides details about all of the seller's locations, including those with an inactive status."). A day is cut at the location's local midnight; a payment in another currency than the location's is refused.
UNVERIFIED: whether `created_at` is always UTC (the connector reads the offset it is given and converts); the largest window one account can read without a rate limit.

**Errors.** https://developer.squareup.com/docs/build-basics/handling-errors: "Error responses include an errors array with an Error object for each error" with `category`, `code` and `detail`. 401 `AUTHENTICATION_ERROR`: `UNAUTHORIZED`, `ACCESS_TOKEN_EXPIRED`, `ACCESS_TOKEN_REVOKED`, `CLIENT_DISABLED`. "If your application sends a high number of requests to Square APIs in a short period of time, Square might temporarily stop processing your requests and return RATE_LIMITED errors with a 429 Too Many Requests status", and the page says to retry "with an exponential backoff schedule" and "a randomized delay (jitter)".
| Code or status | The connector does |
|---|---|
| `UNAUTHORIZED`, `ACCESS_TOKEN_EXPIRED` (401) | `AuthExpired` |
| `ACCESS_TOKEN_REVOKED`, `CLIENT_DISABLED`, a 403 | `AuthRevoked` |
| `RATE_LIMITED` (429), any 5xx, category `API_ERROR` | retried with a bound; a numeric `Retry-After` sets the wait |
| anything else | `UpstreamBroken` |

UNVERIFIED: a `Retry-After` header and any numeric rate limit (the Rate limits page was a 404). A 200 that carries an `errors` array is a failure and is refused.

## QuickBooks Online

**The call.** Pages: https://developer.intuit.com/app/developer/qbo/docs/learn/explore-the-quickbooks-online-api/data-queries and https://developer.intuit.com/app/developer/qbo/docs/learn/rest-api-features.
"Use a GET operation and include the select statement as a URI parameter: https://quickbooks.api.intuit.com/v3/company/<realmId>/query?query=<select_statement>". Select statement: `SELECT * | count(*) FROM IntuitEntity [WHERE WhereClause] [ORDERBY OrderByClause] [STARTPOSITION Number] [MAXRESULTS Number]`. "Multiple clauses (filters) use AND. ... The OR operation isn't supported." Operators include `>=` and `<`. "The maximum number of entities that can be returned in a response is 1,000. If the result size isn't specified, the default number is 100." The sandbox base is `https://sandbox-quickbooks.api.intuit.com` (the Invoice page). Headers: "Accept ... Use application/json for most API interactions" and `Authorization` "required for all requests".
The query is `SELECT * FROM Invoice WHERE TxnDate >= '..' AND TxnDate < '..' ORDERBY TxnDate, Id STARTPOSITION n MAXRESULTS 1000`. UNVERIFIED: that a `STARTPOSITION` page boundary is stable only with a named order; the connector names one (`ORDERBY TxnDate, Id`) so it cannot move a row, and refuses an invoice that appears twice.
**The invoice.** https://developer.intuit.com/app/developer/qbo/docs/api/accounting/all-entities/invoice: `TxnDate` (a date), `TotalAmt` ("the total amount of the transaction. This includes the total of all the charges, allowances, and taxes."), `Balance` ("The balance reflecting any payments made against the transaction. Initially set to the value of TotalAmt. A Balance of 0 indicates the invoice is fully paid."), `CurrencyRef`, and the JSON query response `{"QueryResponse": {"startPosition", "totalCount", "maxResults", "Invoice": [...]}}`. Amounts are JSON numbers (`"TotalAmt": 362.07`), so the response is parsed with `parse_float=Decimal`. UNVERIFIED: that the `Invoice` key is absent when nothing matches (the pages show only a populated answer); the connector reads an absent key as none and the stand-in leaves it out.
**Voided.** The Void operation on the same page: "void an existing invoice object ... The transaction remains active but all amounts and quantities are zeroed and the string, Voided, is injected into Invoice.PrivateNote". A voided invoice is not counted.
**Company.** https://developer.intuit.com/app/developer/qbo/docs/api/accounting/all-entities/companyinfo: `CompanyInfo.CompanyName`; `verify()` reads it. The pages read do not give the company's home currency (`Country` only), so the currency is each invoice's `CurrencyRef.value`; a company that wants zeros written for an empty window states its currency (`QUICKBOOKS_CURRENCY`).

**Errors.** https://developer.intuit.com/app/developer/qbo/docs/develop/troubleshooting/error-codes. "200 OK The request succeeded. However, the response body may contain a <Fault> element that identifies the error." Fault types: `ValidationFault`, `SystemFault`, `AuthenticationFault`, `AuthorizationFault`. Statuses: 400, 401 ("the token in use ... is either expired or revoked"), 403, 404, 500, 503, and `429 Rate limit exceeded` in the code table.
| Fault or status | The connector does |
|---|---|
| `AuthenticationFault`, 401 | `AuthExpired` |
| `AuthorizationFault`, 403 | `AuthRevoked` |
| `SystemFault`, 429, 5xx | retried with a bound |
| `ValidationFault`, other 4xx | `UpstreamBroken` |

UNVERIFIED: the JSON spelling of a Fault (the pages show the XML form); the connector reads `Fault` at the top of the body and inside `QueryResponse`.
**Rate limits.** https://static.developer.intuit.com/output_html/qbo/docs/learn/limits-and-throttles.html: "500 requests per minute per realm ID. 10 requests per second, per realm ID and app." and "You'll see HTTP Status Code 429 when throttling occurs. If you see this, wait 60 seconds before retrying the request." A 429 without a `Retry-After` is a wait of 60 seconds, which is longer than the default cap, so the runner owns it.

## Shopmonkey

**The call.** Pages: https://shopmonkey.dev/overview, https://shopmonkey.dev/quickstart and https://shopmonkey.dev/resources/order.
"API Base URL https://api.shopmonkey.cloud", "The current version of the API is v3 and will be the first part of the path for any URL." "Shopmonkey employs OAuth Bearer Tokens as a method for authenticating API requests." A key is made at "Settings > Integration > API Keys", "Only Admins can create API Keys", "All API Keys will be created with the same permissions and access as the user who creates them", and "the API key cannot be viewed again". `GET /v3/auth/api_key/status` checks a key. `GET /v3/order` is "List Orders - Find all Orders" with the query parameters `ids`, `limit` ("the limit on the number of records to return"), `orderby`, `params`, `skip` ("the number of records to skip for a paginated result"), `where` ("an object to use for filtering the results") and `include`. The response is `{"data": [..], "meta": {"hasMore": "if there are more records available", "total": "the total number of records"}, "success": "if successful, will be true"}`.
**The window is cut in the connector.** The pages name `where` and `orderby` and give no syntax for either, so none is invented: the connector pages through the orders with `limit` and `skip` and keeps the ones whose dates fall in the window. That is a full scan of the shop's orders per sync, so it is bounded (500 pages) and a larger shop is refused with a message. UNVERIFIED: the largest `limit`; the order the list comes back in (so no early stop is taken); the `where` syntax.
**The order.** Fields in the saved example object: `id`, `number`, `createdDate`, `invoiced`, `invoicedDate`, `totalCostCents`, `deleted`, `locationId`, `status`, `workflowStatusId`. A job is booked when its order is created and earns when it is invoiced, so `work_orders` is counted on `createdDate` and `work_order_revenue` sums `totalCostCents` of orders with `invoiced` true on `invoicedDate`; a deleted order is not counted. UNVERIFIED: that `totalCostCents` is the invoice total including tax (it sits beside `taxCents` and `feesCents` and the page does not define it); the timestamp form of the dates (the connector reads ISO 8601, taking a missing offset as UTC); and the shop's currency and time zone, which the order does not carry, so the caller states both (`SHOPMONKEY_CURRENCY`, `SHOPMONKEY_TIME_ZONE`).

**Errors.** https://shopmonkey.dev/overview: "Making API requests without authentication or with an incorrect key results in a 401 HTTP status error, while requests with valid keys but insufficient permissions yield a 403 HTTP status error." Status codes 200, 201, 202, 400, 401, 403, 404, 429 ("your request was rate limited"), 500. The error body is `{"success": false, "code": "API-0efe28", "message": .., "documentation_url": ..}`, and each response carries `x-request-id`.
| Status | The connector does |
|---|---|
| 401 | `AuthExpired` |
| 403 | `AuthRevoked` |
| 429, 5xx | retried with a bound; `Retry-After` sets the wait |
| 400, 404 and any other | `UpstreamBroken` |

**Rate limits.** Same page: "If you are rate limited, you will receive a 429 HTTP status code with information in the headers about when you can retry your request." The headers are `Retry-After` ("The number of seconds to wait before you can submit additional API requests"), `X-RateLimit-Remaining-Minute` and `X-RateLimit-Limit-Minute` ("the number of requests an API key can make in a rolling 60 second window"). The numeric limit is not on the page ("Please reach out to support for more information about our rate limits"). The connector honours `Retry-After` and does not pace by the remaining count.

## What the stand-ins invent

Everything not quoted above. For all five: the text of error messages, the request ids, the cursor and page token forms, which port they listen on. Google Ads: the page size lowered for tests, that a day without activity has no row, that no developer token is required. TikTok: HTTP 200 with a non-zero `code` for an error, the `stat_time_day` form, that `end_date` is inclusive, a default `page_size` of 10. Square: that `end_time` is inclusive (flippable), that the version header is optional, the 400 on a bad parameter. QuickBooks: the JSON spelling of a Fault, the 400 on a validation fault, that `Accept: application/json` is required. Shopmonkey: the largest `limit`, creation order, the shape of the key status answer. None of them can tell you how a vendor restates a figure after the fact, how long a recent day takes to settle, or what a real account with no data sends.
