# Monthly report

The report stage reads the dated snapshots the sync already stored for one connection, works out a month's KPI table and the change on the month before in plain code, has a writer put the narrative into words from figures that passed a check, and saves a PowerPoint deck. It reads stored rows only and never calls a vendor API, the same rule the dashboard follows.

A tenant has one store (Shopify) and may have three more sources: a website (Google Analytics 4), paid media (Meta ads) and search (Google Search Console). Each one adds its figures next to the store's and its own slide, and only the store is required: a tenant with the store alone gets the seven slide deck it always had. The website half is described under [The website source](#the-website-source), the ad and search halves under [The paid media source](#the-paid-media-source) and [The search source](#the-search-source), and the monthly clock under [The monthly run](#the-monthly-run). What each vendor's pages said, and what is UNVERIFIED, is in [GA4_SOURCES.md](GA4_SOURCES.md), [META_SOURCES.md](META_SOURCES.md) and [GSC_SOURCES.md](GSC_SOURCES.md).

**What ran and what did not.** The Meta and Search Console sides were tested only against stand-in servers on 127.0.0.1 written from each vendor's documentation; no ad account and no Search Console property is held and neither connector has run against a live one. The sample deck is invented figures. The n8n workflow was imported and executed in a real n8n container, node by node ([test-runs/2026-10-26-n8n.txt](test-runs/2026-10-26-n8n.txt)); no SMTP server, Slack workspace or Make or Zapier account was used (Slack was a stand-in webhook on the loopback address), and nothing here says anything about Make or Zapier beyond the endpoint they would call.

## Run it

Commands below assume the virtual environment from the README is active, so `python` is its interpreter (activate with `. .venv/Scripts/activate` in Git Bash on Windows, `. .venv/bin/activate` on macOS or Linux). Everything here was run on Windows 11 with Git Bash; the macOS and Linux forms are the standard venv layout and were not run.

```bash
export DATABASE_URL="postgresql://analytics:analytics@localhost:5433/analytics"
python scripts/monthly_report.py --month 2026-10 --tenant <tenant uuid> --dump
```

`--connection <uuid>` names the store and is needed when a tenant has more than one active store connection (two would be added into one doubled total, so the command refuses instead). `--web-connection <uuid>`, `--paid-connection <uuid>` and `--search-connection <uuid>` do the same for a website, an ad account and a search property: a tenant with one active connection of a kind gets it automatically, with two it must name one, and an id that is not an active connection of that kind for this tenant is refused. `--out` names the deck, `--no-model` forces the template narrative, `--data-note` prints a line on the title slide, and `--as-of YYYY-MM-DD` treats that date as today. Without it, today is the UTC date, because the connector buckets every order by its UTC day. Exit 0 means a deck was written. Exit 2 means the report could not be produced, with the reason on stderr.

The narrative is written by a model only when `GROQ_API_KEY` or `LLM_API_KEY` is set in the environment (the provider and model are the Groq values in `app/ai/catalog_copy.py`, and the command has no flag to change them) and `--no-model` is absent. With no key the template writes it. Which writer ran, and why a model's text was refused if it was, is printed by the command, kept in the deck file's comments property and shown by `--dump`. It is not printed on any slide.

## Days: with orders, with no orders, with no data

The Shopify connector writes a row only for a day that had orders. So a day without rows is one of two different things, and the report keeps them apart. The deck says it in plain words, the code calls them data, quiet and missing:

* **Days with orders** (data): the day has at least one snapshot row.
* **Days with no orders** (quiet): no row, and a sync run that succeeded (or finished `partial`) has a window covering the day. The sync looked and found no orders. It adds zero.
* **Days with no data** (missing): no row and no such run covers the day. Nobody looked. A failed run is not coverage.

The three add up to the days in the month (or the days counted so far, for a month that is not over). Sync windows are half open, so a run ending on the 10th does not cover the 10th. Totals add the days that have orders. The days with orders plus the days with no orders are the **reported days**.

A total over fewer reported days is smaller for that reason alone, and can even fall while every reported day rose. So when a month has days with no data (or is not over, or its baseline month has days with no data) the report does not state a direction from the raw totals alone. The headline gives the total plainly and the change per reported day next to it ("October net sales total is 1.8% below September, but October is missing 2 days: per reported day it is up 1.6%"), and each total's sentence in the narrative does the same. Per reported day is the total divided by that month's reported days, computed from the exact values. A complete month keeps the plain headline ("Net sales rose 50.0% from September") with no caveat. The averages (average order value, buyers per active day) are not totals and keep the plain form with the caveat after them.

The KPI table keeps the raw totals and their change, and its Note column names the month and, for the four totals, the change per reported day ("October partial: 2 days missing; per reported day up 6.6%"). The charts show a day with no orders as a dot on the zero line on each plotted line, and a day with no data as a break in the line with an X on the zero line (grey for the previous month), and the footnote says which are present and how many of the days are plotted. A month that is not over only counts the days that are over, and says how many.

A previous month that was synced and found nothing is a **zero baseline**: the change in units is shown, the percentage is "n/a". A previous month with no rows and no run is **no previous month**, a different fact. A baseline note and the partial data note are both kept on a figure. A synced month with no orders prints its order count as 0, and its money totals as 0 when neither month has a money row, otherwise as a zero amount such as $0.00.

## The website source

**Which connection.** Every active connection whose platform is not `ga4` is a store, and `ga4` connections are websites. The store is chosen as before. A website is read from its own rows and its own sync runs, so the days are classified per source: the store can have a day with no data that the website has, and the other way round.

**Days.** A month of website rows goes through the same `month_stats` as the store's. A day with a row is data. A day with none that a succeeded or partial website run covers is quiet (a zero). A day with none and no covering run is missing, left out of the totals and drawn as a gap. GA4 leaves out a day whose metrics are all zero, so quiet is the normal state of a day with no traffic, and a failed run over a day is not coverage.

| Figure | How it is computed |
|---|---|
| Sessions, Page views, Key events | The sum of the daily values over the days that have data. The change on the month before, and in a partial month the change per reported day, work as for the store's totals. |
| Users per active day | The mean of the daily distinct user counts over the days that have data, one decimal, rounded half up; the percent change is from the unrounded means. Distinct counts cannot be added across days (a visitor on two days would count twice), so there is no monthly total. |
| Order rate | Orders divided by sessions, as a percent, over the days **both** sources reported (data or quiet). A day only one source covers is left out of both sides, because a sum over unequal days is not a rate. It is not a GA4 conversion rate: no GA4 event is in it, and orders the website did not send are in it. "n/a" when those days have no sessions. The change column is in points ("+0.2 pts"), the percent column is the relative change. |

A month with no website rows and no covering run has no figures, shown as "n/a" and "not reported", never as zero.

**Weeks.** The weekly table sets sessions against orders for days 1 to 7, 8 to 14 and so on, over the days both sources reported, and says how many ("5 of 7"). A week with no such day prints "n/a" in every column.

**Two calendars.** Store days are UTC days (the Shopify connector converts). The pages do not say how GA4 cuts a `date`; it is probably the property's reporting time zone, which is UNVERIFIED (GA4_SOURCES.md). The report lines the two sources up by date label and says so under the website table. It does not shift either one.

**The check on the narrative.** The website figures are facts in the same shape as the store's (`Sessions`, `Sessions change percent`, `Sessions per reported day` and so on), so the figure check holds each one beside its own metric. Sessions, users (also visitors), page views (also views), key events and order rate have the synonyms the check accepts; a sentence that names a metric the report does not have ("conversions") carries no figure it can ground and is refused. The template prints a line for sessions, key events and order rate, and the check runs over it as it does over the store's.

## The paid media source

**Which connection.** A `meta` connection is the ad account; a tenant has one, or names one with `--paid-connection` (or `paid_connection_id` in the request). The days are classified from the ad account's own sync runs, never the store's: a day with a row is data, a day with none that a succeeded or partial run covers is quiet (the account delivered nothing), a day with none and no covering run is missing and drawn as a gap. A failed run is not coverage.

| Figure | How it is computed |
|---|---|
| Ad spend, Impressions, Clicks | The sum of the daily values over the days that have data, with the change on the month before and, in a partial month, the change per reported day. Clicks are all clicks, not link clicks. |
| Click through rate | Clicks over impressions of the month, as a percent to two places, from the sums. It is never an average of daily rates (a day of 1 click in 1,000 and a day of 90 in 100 are 91 in 1,100, 8.27 percent, not 45), and Meta's own rate is not stored. |
| Cost per click | Ad spend over clicks, rounded half up to the minor unit. "n/a" with no clicks. |
| Purchases, Purchase value | The sum over the days that carry them. A row with no purchase list at all has no purchase figure, which is not a zero, so the table says how many days a figure covers ("on 27 of 29 days") and a month with none shows "n/a". A day's purchase value is its row, or 0 when its purchase count is 0 in a month that has a value row on some day, because Meta leaves a zero out of `action_values`. |
| Return on ad spend | Purchase value over ad spend, over the days that have BOTH, a day's value being as above. A day with spend and a purchase count of 0 is in both sides at 0 value, so it pulls the ratio down as it should (20 days of EUR 100, ten of them worth EUR 300, is 1.50, not 3.00). A day with spend and no purchase figure at all, or with purchases and no value row, is left out of both sides, so it cannot pull the ratio down, and so is every day of a month with no value row at all (a pixel that sends counts and no values), whose value and return stay "n/a". Click through rate, cost per click and position take both sides from the same days because a connector writes a day's spend, impressions and clicks (or clicks, impressions and position) together; `test_output_round_2_classes.py` derives those day shapes from the connectors and checks each ratio over every mix. |

**Money is the ad account's, not the store's.** Ad spend and purchase value are in the account's currency, which need not be the store's (the sample's store is in dollars and its ads in euros). They are shown in their own currency, never added to, taken from or divided by a store figure; a month whose rows name two currencies, or two months in two, is refused as the store's are. The narrative check holds an ad amount to the ad currency: "$6,215.05" about euro spend is refused.

**Which purchases.** Meta's own count, in the 7 day click window the connector names in every request (the page's default is two windows, so leaving it unnamed would let Meta change what a purchase means). It is not the store's orders, the two are never reconciled, and the slide says so. Only `omni_purchase` is read; the other purchase action types may describe the same purchase (UNVERIFIED), so they are not added ([META_SOURCES.md](META_SOURCES.md)).

**Provisional days.** A purchase can arrive after the day is over, inside the click window, so the last 7 days before the report date are marked provisional on the summary table, the paid slide and the data health slide. It is arithmetic on the report date, not a flag read from a row: the same stored rows and date give the same marks, and a month reported more than a week after it ended has none.

**Time zone.** Meta reports a day in the ad account's time zone and the store's days are UTC; the report lines them up by date label and says so under the table, as for the website.

## The search source

**Which connection.** A `gsc` connection is the property, named with `--search-connection` when a tenant has more than one. Days are classified from its own runs, as above. A day with no data is left out of a date query, so a quiet day has no row.

| Figure | How it is computed |
|---|---|
| Search clicks, Search impressions | The sum of the daily values, with the change on the month before and the change per reported day in a partial month. |
| Search click through rate | Clicks over impressions of the month, from the sums, to two places. Google's own rate is not stored. |
| Average position | Each day's average position weighted by that day's impressions (a day of 10 impressions at position 1 and a day of 10,000 at position 10 average 9.99, not 5.5), to one place. A lower number is nearer the top; there is no monthly total and no per reported day figure. |

**Top queries and pages.** For each day with data the connector asks Search Console for that day's top queries and top pages and stores them in their own table (the snapshot key has no room for a query). The report adds a key's daily rows over the month and ranks by clicks, then impressions, then the key, so the order is the same every time, and shows five of each with long keys cut to fit the cell. These are the top rows Search Console returns, "not all data rows": a query that is never among a day's top rows is not counted, so every figure is a lower bound for its key and not a total of the month, and the slide says so.

**Provisional days.** The data takes days to settle ("typically available after 2-3 days"), so the connector asks for fresh data and stores the newest days marked, and the report marks the last 3 days before the report date, by the same arithmetic, on the same three slides. The next sync rewrites them with the settled figures.

**Time zone.** Search days are Pacific days, which the page states, against the store's UTC days; the footnote says so.

## The monthly run

`POST /api/reports/monthly` builds the month's deck for the tenant of the API key (never a tenant named in the request) and answers with a short description (status, slides, sources, the SHA-256 of the deck, the narrative lines, whether it was delivered). `GET /api/reports/monthly/{month}/deck` returns the deck and `POST .../delivered` records that the message carrying it went out. Operators and admins may build and mark delivered, viewers may read; everyone is tenant scoped by row level security, so a key from one tenant never touches another's runs.

**Idempotent by key.** The caller sends one `Idempotency-Key` for one tenant and one month. The first call with it builds the deck and keeps it (table `report_run`, migration 009); every later call answers `"status": "replayed"` with the same bytes, builds nothing, does not read the data again (a figure that moved since is not in the old deck; a new key reads the moved figure) and carries the delivered flag. Two calls at the same moment are arbitrated by the database (`unique (tenant_id, idempotency_key)`): one builds and the other gets 409 with `Retry-After`. A key used for another month is a 422. A failed run (422 with the reason, or 500 with none) may be retried with the same key once the cause is fixed, and a run left `running` for a quarter of an hour by a process that died is taken over by one compare and set.

**The workflow.** [n8n/monthly_report.workflow.json](../n8n/monthly_report.workflow.json), written by `n8n/build_workflow.py` (a test checks the committed file is what the script writes). A Schedule Trigger on `0 13 1 * *` (13:00 UTC, after the settled window of the ads, search and website syncs, which end twelve hours behind UTC) and a manual trigger lead to Settings (the month, defaulting to the one before the run, and the tenants from `HUB_TENANTS_JSON`), Split Out makes one item for each tenant, and an HTTP Request node calls the endpoint with that tenant's key, the month, `as_of` when set and any of the four connection ids the tenant's entry carries (a client with two ad accounts needs one), and an idempotency key of `monthly-report:<tenant name>:<month>`, retrying three times, which is safe because of the key. A tenant that fails (its report cannot be built, or its key is wrong) goes down the node's error output and becomes a result of "failed" while the next tenant is built. A deck already delivered is skipped; otherwise, with a toggle on, the summary goes to Slack and the deck is fetched and emailed, then `POST .../delivered` records it. Every result is gathered into one list; if any failed, a Slack alert goes out when Slack is on and Stop and Error ends the execution as an error naming each failed tenant and why. Delivery is off unless `DELIVER_SLACK` or `DELIVER_EMAIL` is `true`. It uses no Code node and no Execute Command node, which n8n 2.x disables by default; it needs `N8N_BLOCK_ENV_ACCESS_IN_NODE=false`, because it reads its settings from the environment ([n8n/README.md](../n8n/README.md)).

**Really run.** `n8n/verify_in_docker.py` makes a scratch database with invented tenants, starts the API and a stand-in Slack webhook on the loopback address, and imports and executes the workflow in seven throwaway n8nio/n8n 2.44.6 containers, reading the execution JSON node by node (saved in [test-runs/2026-10-26-n8n.txt](test-runs/2026-10-26-n8n.txt)). Run 1 with delivery off: the two tenants that work are built (10 and 7 slides), one with no store (422) and one with a wrong key (401) go down the error output, nothing is sent, and the execution ends as an error naming both. Run 2, the same month again: the endpoint answers "replayed" with the same SHA-256 for both tenants and the database is unchanged. Run 3 with Slack on: one summary for each tenant that works and one alert naming both that failed, and both decks are marked delivered. Run 4, again: both tenants are skipped as already delivered, the Slack post node does not run, and the only new message is the alert. Run 5, only the tenants that work: the execution succeeds and finishes, with no alert. Run 6, email on with no SMTP credential, another month: the deck is fetched, the email is not sent, both tenants are failed results, nothing is marked delivered and the execution is an error. Run 7, two tenant entries that carry a `paid_connection_id`: the one that names the real ad connection is built with its ads (10 slides) and the one that names an unknown connection is refused with the hub's own reason, so the id reached the request body through n8n's own expression engine. The schedule was read back by the `cron` library inside the image: `2026-11-01T13:00:00.000Z` and the five months after it.

**What the real run found.** Two faults no file check could, both fixed and pinned. Every IF read its left value as the literal text `$json.delivered` (a missing `{{ }}`), so each stopped the execution with "is a string but was expecting a boolean". And the Send Email node has no error output: with no credential, n8n 2.44.6 recorded "Node does not have any credentials set" and passed its input item on as if the mail had gone, so the tenant was marked delivered though nothing was sent. The workflow now reads the node's answer (the recipients the mail server accepted) before marking anything.

**Make and Zapier.** None was built or run and no account is held. The call the workflow makes is a plain authenticated HTTP request with an idempotency header, so a Make scenario or a Zap would make the same one; nothing here says more than that.

**What this does not do.** Delivery is at least once: if a send succeeds and marking it delivered fails, the next run sends again (the result says so). A 409 that outlasts three retries a few seconds apart is a failed result for that run. The tenants and their API keys are read from an environment variable, which is the n8n service's to protect. The schedule was checked by evaluating its cron expression and by running the Schedule Trigger node in n8n; the first of the month has not been waited for.

## The KPI table

| KPI | How it is computed |
|---|---|
| Orders, Gross sales, Refunds, Net sales | The sum of the daily values over the days that have orders. Money stays an integer in minor units and is formatted exactly (Decimal; dollars print as `$`, other currencies keep their code, zero decimal currencies such as JPY are not scaled). |
| Average order value | Gross sales divided by orders for the month, rounded half up to the minor unit like every other figure (two orders worth 19.99 together print $10.00, not $9.99). "n/a" when the month has no orders. |
| Buyers per active day | The mean of the daily distinct buyer counts, one decimal. Distinct counts cannot be summed across days, so there is no monthly total. "n/a" (never zero) when the connection withheld the metric. |
| Change | This month minus the previous month, in the metric's own unit, from the displayed figures. |
| Change % | Change divided by the absolute previous value, one decimal, rounded half up. The buyers percentage is computed from the unrounded means. "n/a" for a zero baseline. A rounded `-0.0` prints as `0.0%`. |

The words for a change: "up 8.4%" or "down 12.4%". "Unchanged" only when the two exact, unrounded values are equal. A change that merely rounds to 0.0%, or whose displayed amount is zero, is "essentially flat" and says by how much ("essentially flat (+$4.00)", or "(+0.5%)" for buyers whose means both print as 8.0).

## The narrative and the figure check

`report_facts` reduces the report to a flat set of facts using the very strings the deck prints: dollars as `$40,249.02`, dates as `Oct 14`, months by name with no year, and each total's per reported day figures. Two writers turn them into lines:

* The **template** is fixed wording filled from those strings. It is used when no model key is set, and as the fallback below.
* The **model writer** reuses the catalogue copywriter's transport and error handling (`CatalogCopyWriter._complete`, which takes a system prompt) with a report prompt. It is sent the facts, never a raw row.

Either way the text goes through `ungrounded_numbers`. It runs the catalogue check first (`verify_grounded`, a substring test that the catalogue copy keeps unchanged), then the report's own exact check:

* every amount, percentage, count and date must be one of the facts' displayed figures, written the same way, and an amount must be in the facts' currency ("EUR 210.00" on a USD store is refused; a symbol and its code are the same currency). A year or a day number is never borrowed from a date;
* a sentence that carries a figure must name a recognised metric, and the figure must be that metric's own. Metrics are named by their label or a synonym: net sales, gross sales, sales and revenue (either of the two), orders, order count, refunds, average order value, basket size, buyers, customers, shoppers. A sentence that names no metric may carry only day counts and dates, so "Net sales were $210.00. It rose 33.3% from September." is refused. A bare count beside a metric must be a day count ("2 days", "9 of 31 days");
* a comma between digits must be a valid thousands separator, so "1,4%", "6,07" and "20,15" are refused;
* a figure glued to a letter ("USD9", "x5", "Q4") is still a figure;
* number words are whole words from a fixed list and are refused unless the facts hold the same word: counts (fifteen, dozen, hundreds), multipliers (doubled, twofold, tenfold), fractions and positions (a third, a quarter, first, second), and couple, pair and several. "One" is not found inside "none".

A model's reply is also cleaned before it is checked: markdown emphasis, heading marks and list markers are stripped, and a line that ends with a colon (a preamble such as "Here is the commentary for October:") is dropped. If the reply then fails any check, has more than six lines or an exclamation mark, or has no text, or the provider errors, the whole reply is dropped and the template is used. The template goes through the same function, and the build fails if it ever quotes a figure that is not a fact. When unsure the check refuses, because the fallback is the template.

The ad and search figures are facts in the same shape, so the same check holds each one beside its own metric: Ad spend (also ad cost, advertising spend), Impressions, Clicks, Click through rate (CTR), Cost per click (CPC), Purchases, Purchase value, Return on ad spend (ROAS), Search clicks, Search impressions, Search click through rate and Average position (position). An ad amount must be in the ad account's currency, which is the fact's own: "EUR 180.00" passes and "$180.00" is refused, and the store's net sales figure beside "ad spend" is refused as an ad figure beside a store metric is. Clicks (ads) and Search clicks are different metrics, so a sentence naming search clicks may not use the ad figure and the reverse. A rate is held to its two places and a position to its one ("4.4%" for "4.38%" is refused), a return computed over all the spend instead of the days that carry both figures is refused as not a computed figure, and "conversions" names no metric, so a figure beside it is refused. The provisional days are facts as dates, so a sentence about them can name only those dates.

### Known limits of the figure check

Each of these is pinned by a test, so none can change silently.

* A figure of the right metric in the wrong role passes (September's net sales written as October's).
* A wrong direction word and a dropped minus sign pass ("fell" about a rise, "rose 86.4%" for a fall of 86.4%).
* The metric check is per sentence: a sentence that names two metrics may use either one's figures.
* Day counts and dates are interchangeable between the data health facts (2 days with orders can be written as 2 days with no orders; the best day's date can be written as a day with no data).
* A correct sentence written in another format is refused and the template is used ("33%" for "33.3%", "Oct 10-11" for "Oct 10, Oct 11").
* Claims and causes are not checked ("a record high", "because of the holiday sale"). The prompt forbids them and the KPI table carries the true direction.

## The deck

Seven slides for a store with no website: title, KPI summary table, net sales by day (this month against last month), orders by day, order value and buyers with the three best days, insights, data health.

With a website the deck is eight slides, not seven, for a reason: the website is a second source with its own days, so it needs its own table and its own data health, and the KPI slide was full. The orders chart moves beside a new sessions chart (slide 4, two charts, each against the month before), and a website slide follows the order value slide (slide 6: the website KPI table and the weekly sessions against orders table). The data health slide (slide 8) has one column per source and month and names the days with no data for each. The store only slides are unchanged, and a test compares a store only build with the saved read back of the earlier sample, character for character. Every table cell and title is a string `monthly.py`, `web.py`, `paid.py` or `search.py` formatted; the deck does no arithmetic. The charts are native PowerPoint charts, so the values can be read back with python-pptx. The slides use plain words (days with no data, data pull, daily figures) and no text box or table cell is smaller than 11 points, which a test enforces (chart text is set to 12 points in `deck.py`). The file's own properties are set: author, a creation time of the build, an application name and slide count in place of the template's, and no template thumbnail.

With ads or search the deck grows by a slide for each, in this order: title, summary, net sales, orders (or sessions beside orders when there is a website), order value, the website, paid media, search, insights, data health, so up to ten. The summary table gains a headline row or two for each added source (ad spend and return on ad spend, search clicks and average position), whose Note names the days behind it ("on 27 of 29 days", "last 6 days provisional"), and its footnote names the ad currency and the purchase window. The paid media slide holds the eight ad figures in a table beside two native charts, spend (the axis in the ad account's major units, euros here) and clicks, each against the month before with a break and an X for a day with no data. The search slide holds two charts (clicks and impressions), the four search figures and the top five queries and pages, with long keys cut in the cell and whole in the stored rows. The data health slide has a row for each source (days with data, with nothing to report, with no data, and that may still change) and then names the days with no data for each source and month and the provisional days. A store alone and a store with a website render exactly as before: the saved read-back of the earlier sample and the website tests are unchanged. With ads or search the narrative keeps the store's two headline figures and one or two lines for each source, because nineteen lines ran off the slide in the render.

## Limits

* Four sources, and the store is required: a tenant with ads or search and no store connection gets no report. The ad and search halves have no reconciliation with the store's orders.
* Meta, Search Console and GA4 have never run against a live account. Each stand-in is written from the vendor's pages, and the sources files ([META_SOURCES.md](META_SOURCES.md), [GSC_SOURCES.md](GSC_SOURCES.md), [GA4_SOURCES.md](GA4_SOURCES.md)) list what is UNVERIFIED: for Meta whether the `until` date is inclusive, whether `Retry-After` is sent, how a purchase is split across action types, and the time zone of a day; for Search Console the header form, the shape of a quota error and how far a day is restated.
* The connectors take an access token someone has already obtained. None exchanges a key for one or refreshes it.
* The provisional lags (7 days for ads, 3 for search) are inferences from what the pages say, not values read from a response, and they are applied by arithmetic on the report date.
* The top queries and pages are the top rows Search Console returns for each day, so each figure is a lower bound for its key and never a total of the month.
* The workflow was run for real in n8n 2.44.6, seven times (the output is saved), but not against a live Slack or SMTP server, and the first of the month has not been waited for: the schedule was checked by evaluating its cron expression and by running the trigger node. Delivery is at least once: if a send succeeds and marking it delivered fails, the next run sends again. Make and Zapier were not built or run.
* Three independent review passes have looked at the ads, search, monthly run and deck code (one each for the Meta connector and the paid half, the Search Console connector and the search half, and the run, workflow and deck): they wrote 116 cases from the specs and ran them against the code, and a lead reproduced and scored each finding. Nine findings came back. Four were kept and each fixed once by its class with a generated table: the schedule moved from 06:00 to 13:00 UTC because the ads, search and website syncs end twelve hours behind UTC and the deck was a day short for those three sources (the deck needs each of those syncs to have run after 12:00 UTC on the 1st, which nothing here schedules); a long search key is cut in the middle so five pages of one site no longer print as one; position and cost per click are worded as worse or better, never up or down; and a tenant entry may carry the four connection ids. Five were left as known limits: Meta code 80000 is raised as UpstreamBroken, not as a throttle; the purchase note says "on 29 of 31 days" for two days with no ad delivery; a pasted display name or an id with a trailing space as a connection id gives a 500 and no reason; marking a month delivered picks the run by month, not by key; a page address over 2,048 characters breaks the top row length check. Two keys of more than 30 characters that share their first 12 and last 15 characters still print alike. A second blind round followed (below). No pass was run after it, no live Meta, Search Console, Slack or SMTP account was used, and the passes judged what they were shown, so they are not a proof that nothing else is wrong. The derived guards measure how much the tests pin, and the deck snapshot pins what was read from the rendered pages, which is not a proof that the layout is right.
* A second blind round, by a reviewer on a different model family who read the finished build, wrote 43 cases (20 must pass, 23 must fail), ran them on a copy of it, and a lead reproduced and scored each finding. Three findings were kept and fixed once by class, one was rejected. The return on ad spend took its days from the purchase value rows, and Meta leaves a zero out of `action_values`, so a month of EUR 2,000 spend and EUR 3,000 value printed 3.00 instead of 1.50 (a day's value is now its row, or 0 for a count of 0 in a month with value rows). The default sync window was 30 days back from the end, so a run on 1 November never stored 1 October (it now starts on the first day of the previous month, for ads, search and the website). A sync wrote the account the environment named into the connection it was given, so a variable left over from another client put that client's ad spend and search clicks into this one's deck (a sync now exits 2 when the two do not name the same account, in any spelling). The rejected finding is a limit, pinned by number in `test_hub_corpus_blind_2.py`: a client listed twice in `HUB_TENANTS_JSON` with the same key and two ad accounts gets the latest deck of the month under both entries, the same class as the delivered mark limit above, and it needs a workflow entry nobody writes by accident. Left as limits on purpose: a day with clicks and no impressions row (no connector writes one, it needs a hand edited row); a month with purchase counts and no value row at all, or with a count of 0 on every day and no value row, shows "n/a" for the value and the return, since nothing separates a pixel that sends counts and no values from a month with no sales; the store has no default sync window to check (Sync Now takes a number of days, default 7); and an account stored under a label that is not an account id is now refused by a sync, which stops a wrong write and asks for the connection to be fixed. The fixes were mutated: 103 of 113 killed, the 10 survivors read ([output](test-runs/2026-10-26-output-round-2-mutation.txt)), and the new tests fail on the old code ([output](test-runs/2026-10-26-output-round-2-failing-on-old-code.txt)).
* The sample is invented figures in a scratch database. No real store, property, ad account or client went through this stage.
* The model path is tested only through a mocked transport, so how a real model behaves on the report prompt is unmeasured.
* The figure check has the known limits listed above, and the ad and search figures inherit them.
* Found by an adversary pass over the GA4 and website work and left as known limits: a model's sentence can write users per active day as a monthly visitor count and pass the figure check; the "moved most" line reads only the store's figures; a store with no earlier month still shows the website's earlier month; GA4 sampling is stored on each row but the deck does not say a month was sampled.
* A day Google later reports as all zero sends no row, so the figures stored for it stay (an expected failure in `test_ga4_sync_db.py`).
* The order rate uses the store's orders, all of them, against the website's sessions. It is a ratio of two counts, not a conversion rate.
* One connection of each kind and one currency per report. Money rows with two currencies in a month are refused, not converted. Store days are UTC, ad days follow the ad account, search days are Pacific, and the report lines them up by date label.
* The deck is a fixed layout of seven to ten slides with no template or branding option.
* The catalogue copywriter's own substring check is unchanged. Only the report uses the exact figure check.
