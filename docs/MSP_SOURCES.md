# MSP sources: ConnectWise Manage, Autotask, NinjaOne

What the three MSP connectors (`app/connectors/connectwise.py`, `autotask.py`, `ninjaone.py`) and their stand-in servers (`connectwise_fake.py`, `autotask_fake.py`, `ninjaone_fake.py`) were written from. The saved pages are in [vendor-contract/](vendor-contract/README.md#msp-connectors), each with the address it came from and the date it was read (2026-11-29). A quote under a fact is copied from a saved page. A fact the pages did not give is marked UNSTATED here and in the code, and it stays that way until a real account answers.

No ConnectWise, Autotask or NinjaOne account is held and none was used. All three connectors were written from published documentation and tested against a stand-in server on 127.0.0.1; nothing here is a statement that any of the three vendors accepts these requests. A stand-in is written from these pages and refuses what they say the vendor refuses, and it invents only what is listed at the end of each section.

## ConnectWise Manage (PSA)

**The pages are not ConnectWise's own.** The developer documentation (developer.connectwise.com) needs a login. Its registration form refuses a free mailbox address ("We noticed that you are not using a corporate email address. Please use a corporate email account to register."), and no account was made ([what was tried](vendor-contract/connectwise/connectwise-developer-portal-not-retrieved.txt)). The ConnectWise connector therefore rests on two saved files that are not read from ConnectWise's portal, and it is weaker evidence than the Autotask and NinjaOne sections:

- [connectwise-manage-openapi-extract.txt](vendor-contract/connectwise/connectwise-manage-openapi-extract.txt): an extract of the Manage OpenAPI file ("Connectwise Manage Public Endpoints", version 2026.11) as an open source client library keeps it in its generator folder (https://github.com/covenanttechnologysolutions/connectwise-rest). It gives the paths, the parameters and every ticket and time entry field name. Whether it is a faithful copy of ConnectWise's own swagger cannot be checked here.
- [connectwise-pagination-the-lazy-administrator.txt](vendor-contract/connectwise/connectwise-pagination-the-lazy-administrator.txt): a blog post by an independent author that shows real request and response headers (https://www.thelazyadministrator.com/2024/06/06/how-the-connectwise-manage-api-handles-pagination-with-powershell/).

**Authentication.** The OpenAPI file's only security scheme is `{"type": "http", "scheme": "basic"}` and every call lists a required header `clientId`. The blog builds the string as `$apiKey = "{0}+{1}:{2}" -f $authcompanyID, $publicKey, $privateKey`, Base64 encodes it for `Authorization: Basic ...`, and sends `clientId` beside it. The connector sends exactly those two headers. UNSTATED by any saved page: how a `clientId` is obtained (the connector's registry hint says the ConnectWise developer network, which comes from third party search results that were not saved), and the status for a wrong key (the connector reads a 401 as "a person must fix the keys", which third party sources say but no saved page does).

**The calls.** The OpenAPI file's server is `http://na.myconnectwise.net/v4_6_release/apis/3.0`; the cloud host depends on the tenant's region and is the operator's to give (`api_url`, https, up to and including `/apis/3.0`). The connector reads `GET /service/tickets`, `GET /time/entries`, `GET /system/info` (the cheapest call, `verify()`), and, only when `refresh_open_sla` is on, `GET /service/tickets/{id}`.

**Paging.** The OpenAPI file lists `page`, `pageSize` and `pageId` on every list call and describes none of them. The blog does: "PageSize: How many items are returned per page. The max is 1,000"; "Forward-Only was released in 2018.5 ... To use this method, you must include pagination-type: forward-only in your request header. The forward-only method will return a single link in the Link property, and that will be the URL for the next page of data."; "PageID: Used for Forward-Only pagination. Treated like an additional condition of Id > pageId". The connector sends that header and `pageSize=1000`, follows `Link: <...>; rel="next"` exactly as given, and never follows one that is off the host or outside the API path. UNSTATED: what happens to a forward-only list when a record is added while it is read (the connector reads in id order, which is how pageId behaves, and refuses a repeated record).

**Windowing.** UNSTATED on any saved page: the `conditions` grammar (how a date is written, whether `[...]` brackets are needed). The parameter is in the OpenAPI file with an empty description. The connector therefore sends no `conditions` of its own, reads every ticket and time entry the key can see, and cuts to the window itself. An operator who knows the grammar can pass `ticket_conditions` and `time_conditions`, which go through unchanged. The same goes for `fields`.

**The ticket.** Names read from the OpenAPI `Ticket` schema: `id`, `summary`, `board.name`, `type.name`, `priority.name`, `status.name`, `company.name`, `closedFlag`, `closedDate`, `dateResolved`, `dateResponded`, `respondByGoalUTC`, `resolutionGoalUTC`. The creation time is `_info.dateEntered`: the schema types `_info` only as "object, additionalProperties string", and the blog's reply code reads `_info.dateEntered`, so that one name rests on the blog alone. UNSTATED: the date format of `closedDate`, `dateResolved`, `dateResponded` and `_info.dateEntered` (the schema types them as plain strings; only the three `...UTC` fields say `date-time`), so the connector accepts an ISO 8601 date and time with a zone and refuses one with no zone, rather than calling it UTC. UNSTATED: whether `closedDate` is always present on a closed ticket (the connector refuses a closed ticket without one), and what a priority's `sort` number means (the connector never uses it).

**The SLA times.** The schema's description of `resolutionGoalUTC`, `respondByGoalUTC` and the minutes fields: "To obtain the current SLA times for an active ticket, please use the /service/tickets/calculateSLA endpoint for multiple tickets or /service/tickets/{id} for individual tickets." `calculateSLA` is not among the OpenAPI file's paths, so it is not called. The list's values are used for a finished ticket; for an open ticket `refresh_open_sla=True` re-reads it by id, at one request each. Without it, an open ticket's goal is what the list says, which the schema says may not be current.

**The time entry.** `id`, `member.name` (or `member.identifier`), `timeStart`, `actualHours` (a number), `ticket.id`. UNSTATED: whether `actualHours` is the hours worked or the hours billed (the schema has separate `hoursBilled` and `invoiceHours`, so it is read as worked), and the largest value one entry can hold (the connector's own bound is 24 hours).

**The limits.** UNSTATED by every saved page: a rate limit, a 429, a `Retry-After` header. Third party descriptions found while searching disagree (60 a minute, 1,000 a minute, "no published cap") and none was saved, so none is used. The connector paces nothing, retries a 429 (waiting for `Retry-After` when there is one and backing off when there is not, and handing a wait longer than the retrier's cap to the runner) and a 500, 502, 503 or 504 with a bound.

**What the ConnectWise stand-in invents.** The 401 for a wrong key or a missing `clientId`; a `Retry-After` on a 429; the shape of `/system/info` (the connector reads nothing from it); the page cap a test sets; and the `conditions` parameter, which it records and ignores.

## Autotask PSA

**Pages.** All read in Chromium on 2026-11-29 from autotask.net/help/developerhelp and saved in [vendor-contract/autotask/](vendor-contract/autotask/): [security and authentication](vendor-contract/autotask/autotask-rest-security-and-authentication.txt), [zone information](vendor-contract/autotask/autotask-rest-zone-information.txt), [API zones](vendor-contract/autotask/autotask-api-zones.txt), [supportability, thresholds and latency](vendor-contract/autotask/autotask-rest-thresholds-limits-latency.txt), [thread limiting](vendor-contract/autotask/autotask-api-thread-limiting.txt), [best practices](vendor-contract/autotask/autotask-rest-best-practices.txt), [introduction to calls](vendor-contract/autotask/autotask-rest-introduction-to-calls.txt), [basic queries](vendor-contract/autotask/autotask-rest-basic-query.txt), [advanced query features](vendor-contract/autotask/autotask-rest-advanced-query-features.txt), [entityInformation](vendor-contract/autotask/autotask-rest-entityinformation.txt), [picklists](vendor-contract/autotask/autotask-understanding-picklists.txt), and the [Tickets](vendor-contract/autotask/autotask-entity-tickets.txt) and [TimeEntries](vendor-contract/autotask/autotask-entity-timeentries.txt) entities. Several of them hide their body in collapsed sections that a plain page read leaves out; the saved files are the full text.

**Authentication.** "You'll need to use the API User (API-only) security level to access the REST API." The page's example of the required headers: `Username "apiuser@example.com" Secret "abc123" APIIntegrationcode "ASHJKLFDKAHKASLFH85LSA905H" ContentType "application/json"`. The connector sends `Username`, `Secret`, `APIIntegrationcode` and `Content-Type` (the page's `ContentType` is not an HTTP header name; the standard one is sent). "The REST API requires a tracking identifier for API-only users." "Failed authentication to the REST API will result in the return of a 401 error", which the connector reads as "a person must fix the credentials" (`AuthRevoked`). UNSTATED: the status for a user whose security level lacks access to an entity (the page says such a user "would receive no response to an API call, even though the data exists", so an empty answer can be a permission, and nothing here can tell it from no tickets).

**The zone.** "We recommend that your API integrations make a ZoneInformation request first to determine the proper zone (and accompanying URL) to use for all of the session's API interactions", "ZoneInformation requests do not require authentication", and the example `GET http://webservices.autotask.net/atservicesrest/v1.0/zoneInformation?user=user@companydomain.com` answers `{"zoneName": "America East", "url": "https://webservices3.autotask.net/atservicesrest/", "webUrl": "https://ww3.autotask.net/", "ci": 20264}`. Every zone URL on the zones page is `https://webservicesN.autotask.net/atservicesrest` (two pre-release zones are `prde` and `pres`). The connector asks `https://webservices.autotask.net` (the example's host, over https), sends no credential to it, and sends the credentials only to a zone answer that is https on an `.autotask.net` host with the path `/atservicesrest`, or, when the lookup was itself a loopback stand-in, a loopback address. UNSTATED: whether the lookup host answers https (the page's example is http), and what it answers for a user it does not know (the stand-in answers an empty url, which the connector refuses).

**Queries.** `GET .../v1.0/Tickets/query?search={"filter":[...]}`; the operators in the basic query page's table: `eq`, `noteq`, `gt`/`gte`, `lt`/`lte`, `beginsWith`, `endsWith`, `contains`, `exist`, `notExist`, `in`, `notIn`; grouping `{"op": "or", "items": [...]}`; "GET query strings have a limit of 2048 characters". `IncludeFields` ("For search results that contain more than 500 results, you must include Id as a field"), `MaxRecords` ("The valid range of values for MaxRecords is 1 to 500 per page of results"). Dates: "submit date-time values in the format yyyy-mm-ddThh:mm:ss.ms" and "The REST API stores and returns all time data in Coordinated Universal Time (UTC)", so a time with no zone is read as UTC. The ticket query is one OR group (created in the window; completed in the window; resolution goal in the window; not completed), and the time query a date range on `dateWorked`.

**Paging.** "API responses can return a maximum of 500 results at a time", `pageDetails` holds `count`, `requestCount`, `prevPageUrl` and `nextPageUrl`, "you can use the nextPageUrl value to check for results on additional pages until you encounter a NULL value", and "Do not change the query method, the MaxRecords or IncludeFields values, or any filter criteria while using paging URLs." The connector follows `nextPageUrl` as given and never off the API host and path, and refuses a page whose `count` is not the number of items that arrived. The pages also give the alternative of looping on `id` greater than the last id; the connector does not use it. UNSTATED: whether `count` is always present (a missing one is not an error), and the exact shape of the `paging` value in `nextPageUrl` (the connector never builds or reads it).

**Limits.** "Autotask sets a limit of 10,000 on the number of external requests allowed per hour between an individual database and the API", counting "all integrations", with `GET .../ThresholdInformation` answering `{"externalRequestThreshold": 10000, "requestThresholdTimeframe": 60, "currentTimeframeRequestCount": 2}` and a usage-based latency from 50 percent. "Any integrations developed following the Autotask 2023.1 release have a thread limit of three per object endpoint and tracking identifier" and a second concurrent call to the same object "fails with a 429 error response"; the best practices page says "Serialize your requests". The connector sends one request at a time, reads `ThresholdInformation` once per sync and stops before a call when fewer than 200 of the hour's requests are left (200 is its own margin: no page names one). UNSTATED: the status of a request refused because the hourly threshold is spent (the page says only "you will see an error message and experience a temporary suspension"), and whether any response carries `Retry-After` (the connector uses it when it is there and backs off when it is not).

**The ticket.** Names read from the entity table: `id`, `title`, `createDate`, `completedDate`, `resolvedDateTime`, `resolvedDueDateTime`, `dueDateTime`, `firstResponseDateTime`, `firstResponseDueDateTime`, `status`, `priority`, `ticketCategory`, `issueType`, `companyID`. Picklist fields hold a number: "In the API, you can view picklists by making GET requests to ... /entityInformation/fields", with `isPickList` and `picklistValues` entries of `value`, `label`, `isDefaultValue`, `sortOrder`, `parentValue`, `isActive` and `isSystem`; the connector asks `Tickets/entityInformation/fields` once and shows a number the picklist does not hold as `<field> <number>`. UNSTATED, and handled as follows:

- Which status number means a ticket is complete. A ticket is closed when it has a `completedDate`.
- Which field is the SLA resolution goal. The entity page lists `dueDateTime`, `resolutionPlanDueDateTime` and `resolvedDueDateTime` with no description; `resolvedDueDateTime` is the default and `resolution_due_field="dueDateTime"` is the other offered.
- Whether `serviceLevelAgreementHasBeenMet` agrees with a goal computed here. It is not read.
- Company and technician names: `Companies` and `Resources` are other entities. A company is shown as `company 42` and a technician as `resource 7`.
- The `userAccessForQuery` values: the field table says 0, 1 or 2 and the page's own sample answer shows the words `None`; the connector reads neither.

**The time entry.** `id`, `ticketID`, `resourceID`, `dateWorked` (a datetime), `hoursWorked` (a decimal). UNSTATED: whether `dateWorked` is the day the person worked in their own zone or a UTC instant (the page says all times are UTC; the connector takes the UTC day), and the largest value one entry can hold (the connector's own bound is 24 hours). Time worked on a ticket the window query did not return is matched to its ticket by a second query, `id` `in [...]`, 100 at a time (the connector's own chunk: the pages give a limit of 500 OR conditions and none for a list).

**What the Autotask stand-in invents.** The shape of an error body; the `paging` value inside `nextPageUrl`; the picklist values; field names matching whatever their case; whether a 429 carries `Retry-After` (only when a test sets one); and that no request is ever refused for the hourly threshold.
