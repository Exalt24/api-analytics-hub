# Mutation history and review passes

The long form of what the README's Testing section summarises. Each figure names its output file; the guards were run in a copy of the repository because the harness edits source in place.

**Run dates.** Python: run of 2026-11-07 ([output](test-runs/2026-11-07-full-pytest.txt); the skips are the stripe-mock and pg_dump tests, which run in CI); web: 2026-11-10. The ad and business connectors have their own run ([output](test-runs/2026-11-07-ads-business-pytest.txt)). 22 deliberate breakages of them each turned a test red ([output](test-runs/2026-11-07-ads-business-mutation.txt)).

Of the 300 hand matched guards, 91 are new; the 97 aimed at the report, the services and the migrations went red on 2026-10-26, the 25 for price watch ([output](test-runs/2026-10-30-price-watch-mutation.txt)) and the 35 for billing ([output](test-runs/2026-10-30-billing-mutation.txt)) on 2026-10-30, the 11 for the Stripe SDK on 2026-10-31, and the other 132 were not rerun. The 2026-10-26 code was also mutated from its syntax tree (`tests/derived_guards.py`, driven by the author's `mutate_ast.py`, not in this repository): 2,779 mutants in 14 files, 2,662 killed, 117 survived, 90 of them a `|` in a type annotation and 27 read and equivalent ([table](test-runs/2026-10-26-derived-guards.txt)). Blind review of the ads, search and monthly run code ran 159 cases in four passes: seven findings were fixed by class, six are known limits pinned by tests, and 191 of 201 mutants of the fixes were killed, the rest read ([cases](../tests/corpus), [round 2](test-runs/2026-10-26-output-round-2-mutation.txt), [limits](MONTHLY_REPORT.md#limits)). No pass after the second round was run.

**2026-11-07, the ad platform and business system connectors.** 22 deliberate breakages of the new code (a payment counted on its UTC day, a retry loop that never hands a long wait back, a cost per conversion that divides all spend, a money check that forgets a new key, and others), each run in a copy, each turned a test red ([output](test-runs/2026-11-07-ads-business-mutation.txt)). `tests/test_vendor_common.py` and `tests/test_adspend_view.py` also run their rules over 300 seeded worlds each with mutation controls. No blind review pass has been run on this code.

**2026-11-14, the e-signature slice.** 212 tests in four files (71 with no database, 74 against Postgres as the request role, 16 over HTTP, 51 in the seeded simulation, which plays 50 worlds and then counts the cases they reached) and 9 for the harness itself ([output](test-runs/2026-11-14-esign-pytest.txt)); 63 deliberate breakages of the code and the migration, each run in a copy and each caught by a test it names ([output](test-runs/2026-11-14-esign-mutation.txt)); in `web/`, 27 tests of the portal client and 17 more guards in `scripts/mutation_check.mjs` ([output](test-runs/2026-11-14-esign-web-tests.txt)); the built portal was also driven once in Chromium against a running backend, 16 checks ([output](test-runs/2026-11-14-esign-portal-browser.txt)). The first run of the harness left one breakage alive (the connection address written to a log: the test only sent a forwarded address); a signing without that header was added to the log test and the second run caught all 63. Rules, tests and limits: [esign.md](esign.md).

**2026-11-24, purchase orders and the plan workbook.** 105 more Python tests in five files: 34 for the order rules with no database (the transition table pair by pair, receipts, inbound arithmetic, how the plan reads an order on the way, properties over seeded random walks and worlds), 43 against Postgres as the request role (tenant isolation, an order made from the plan's draft, the expected date, refusals made by the database itself including a hand written UPDATE, receipts, the late alert raised once and delivered through the outbox, and a property test that drives 60 random orders through the database and through the pure rules in lockstep and demands the same answer, refusal for refusal), 12 over HTTP, 3 for the command line and 13 for the workbook, 6 of which recalculate it in LibreOffice and compare every computed cell with `plan_variant` over seeded worlds, with a change of one unit in an input required to fail the check. In `web/`: 13 tests (the legal buttons checked against the database's transition table, the order flow on the real database layer, the workbook request against a stand-in backend), 3 more browser tests, and 25 more guards. Recorded on the development store's plan, with the page driven in Chromium against the real backend ([run](test-runs/2026-11-24-inventory-orders-and-workbook.txt), [guards](test-runs/2026-11-24-inventory-orders-mutation.txt)): 674 computed cells compared, 0 differ, and one lead time changed by one day made 15 differ. 58 more guards in `tests/mutation_check_inventory.py`, each caught after three equivalent ones were dropped and one test was added. The LibreOffice check also ran with the `formulas` package standing in for it, with the same result; CI installs LibreOffice and sets `WORKBOOK_REQUIRE_RECALC=1` so a missing engine fails there.

**2026-11-24, inventory planning.** 87 Python tests in four files: 35 for the rules in `app/inventory/model.py` (hand worked cases, and properties over seeded random worlds: velocity never counts an out of stock day, the reorder point never falls as lead time or service level rises, the classes and labels partition the variants and do not depend on input order), 11 for the Shopify reader against a stand-in written from the documented response shapes, 20 for the alert rules, the webhook sink and the digest (the hub's own alert policy over 300 seeded worlds), and 21 against real Postgres as the request role (tenant isolation on every new table, a sync that keeps what a person set, the stored plan against numbers worked on paper, each shortage raised once, delivery through `app.changes.deliver_pending`). Run against the development store on 2026-11-24 with the output saved ([output](test-runs/2026-11-24-inventory-planning-dev-store.txt)); the browser run of the page is part 3 of that file. 56 deliberate breakages of the module, of the delivery code it shares with change detection and of the migration, each run in a copy and each caught by a test it names (`tests/mutation_check_inventory.py`, [output](test-runs/2026-11-24-inventory-mutation.txt)). The first full pass left three alive (the tie break of the classes, a variant that does not sell on the reorder list, and an order size whose review period was hidden by the minimum order) and a fourth, `<` for `<=` when the shelf empties exactly, changes no answer and was dropped as equivalent; each of the three got a test and the second pass caught all 56. Two breakages of the migration also read as green once because Postgres had gone away and the database tests skipped, so the harness now refuses a run that skips. In `web/`: 22 tests (the purchase order drafts against hand worked totals, the Server Actions on the real database layer, the export files read back as CSV, a workbook and a Sheets paste), 5 browser tests in Chromium, and 32 more guards in `scripts/mutation_check.mjs`, two of which needed a stronger test after the first run (a sort order that coincided with the cover order, and a date pattern hidden by the reversed range check).
